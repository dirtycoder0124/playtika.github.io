                  WildCard XSS PROMPT
=======================================================



You are conducting an authorized XSS assessment against *.storia.ro 
(confirmed in-scope for [bug bounty program / pentest engagement]).

OBJECTIVE: Enumerate all subdomains, discover injectable input points, and 
test for reflected, DOM-based, mutation (mXSS), and stored XSS, then report 
findings with PoC and remediation guidance.

PHASE 1 — RECON / ASSET DISCOVERY
1. Enumerate subdomains: subfinder, amass, assetfinder, crt.sh, dnsdumpster
2. Resolve + probe live hosts: httpx / httprobe
3. Crawl each live host: katana, hakrawler, gospider — capture all URLs, 
   forms, JS files, and API endpoints
4. Extract JS files and pull endpoints/params from them: LinkFinder, 
   getJS + subjs, or manual grep for fetch()/XHR calls
5. Pull historical URLs with known params: gau, waybackurls, 
   Wayback Machine, GitHub dorking for leaked endpoints. Use tor proxy if gau webarchive blocked

PHASE 2 — PARAMETER & INPUT DISCOVERY
1. Extract all query params, form fields, headers (Referer, User-Agent, 
   X-Forwarded-For), cookies, and JSON body fields that get reflected
2. Use Arjun or ParamSpider to find hidden/unlinked parameters
3. Identify reflection points: send a unique canary string 
   (e.g. xss_test_a1b2c3) into every param/header/cookie and diff the 
   response to see where it comes back unmodified

PHASE 3 — REFLECTED XSS TESTING
1. For every reflection point, determine the injection context:
   - HTML body, attribute value, JS string, JS variable, URL, CSS, comment
2. Fuzz with context-breaking probes: 
   "'"><svg/onload=confirm(1)> etc. — tools: knoxnl, XSStrike, Dalfox, kxss
3. Confirm WAF/filter behavior (character blacklist, encoding, length 
   limits) and craft context-appropriate bypass payloads
4. Validate execution in a real browser (headless Chrome via Puppeteer/
   Playwright script that watches for confirm()/alert() firing) — don't 
   rely on grep matches alone, confirm actual execution

PHASE 4 — DOM XSS TESTING
1. Identify dangerous sinks in JS: innerHTML, document.write, eval, 
   location.hash/search assignments, jQuery .html(), postMessage handlers
2. Trace sources (location, document.referrer, window.name, postMessage, 
   localStorage) to sinks — use DOMPurify bypass techniques where 
   sanitization is present but misconfigured
3. Automate with DOM XSS scanners: DOMInvader (Burp), or a custom 
   Playwright script that hooks sinks via a monkey-patched JS proxy and 
   flags when tainted data reaches them

PHASE 5 — MUTATION XSS (mXSS) TESTING
1. Target inputs that pass through innerHTML, DOMPurify, or the browser's 
   HTML parser twice (e.g., sanitize -> serialize -> re-parse)
2. Test known mXSS gadgets (mutation of <noscript>, <template>, malformed 
   tags that get "fixed" by the parser into executable markup)
3. Check any client-side sanitizer/library version against known mXSS CVEs 
   for that library

PHASE 6 — STORED / BLIND XSS (if in scope)
1. Submit XSS payloads with a callback (XSS Hunter Express / self-hosted 
   collector) to every persistent input (profile fields, comments, 
   support tickets, file metadata)
2. Monitor callback server for out-of-band fires across admin panels, 
   emails, logs, etc.

PHASE 7 — VALIDATION & REPORTING
1. For each candidate, produce a minimal reproducible PoC URL/request
2. Screenshot/record proof of JS execution in-browser
3. De-duplicate by root cause (same sink/filter bug across many params)
4. Write up: affected URL, parameter, context, payload, impact, and 
   suggested fix (output encoding, CSP, sanitizer library patch)
